# 卡片典藏调查与优化计划

目标是让新获得的卡片在本次登录中可充能，让玩家直接维护当前卡组，并保留已保存搭配的一键切换。

比对基线为官方 `js-archive` 的 `8e667880943a80a1cbf550407944e4ca270d56da`（`Online.js` 哈希 `bfdae749c826`）和本地 `feat/tauri-native` 的 `f20d54d8a17d56362f84bdc450581c5286e4a02a`。官方界面行为在拆分模块和该版本原始 bundle 中均已核对。[官方归档](https://github.com/parkerjj/LROBrowser/tree/8e667880943a80a1cbf550407944e4ca270d56da)

## 官方功能

| 功能 | 官方客户端行为 |
| --- | --- |
| 浏览 | 游戏菜单打开「卡片典藏」。左侧是「我的卡组」和头饰、铠甲、武器、盾牌、披肩、鞋类、饰品。分类可筛选「全部」「已充能」「可充能」，分类实际按筛选遍历各数据页，分页控件在这版路径中隐藏。 |
| 搜索和物品说明 | 按名称或物品 ID 片段跨装备分类搜索。结果保留每张卡的真实分类、数据页与充能状态。右键卡名或卡图可打开原生物品说明。 |
| 充能 | 「可充能」取背包中有该卡、典藏状态为 `0` 的条目。玩家确认消耗一张后发送充能请求，收到状态 `1` 后显示可加入。获得卡片只改变背包持有量。 |
| 加入和移除 | 状态 `1` 的卡片可加入「我的卡组」，回包状态 `2` 表示已加入。已加入的卡片在分类、搜索中显示「已添加」，从「我的卡组」移除。原版这两步也有确认框。移除结果使用服务器回包状态更新。 |
| 卡组效果和限制 | 界面说明加入后会自动绑定指定类型装备并处理效果，最多 8 张，与装备上相同的卡片只生效一份，支持精炼与套卡效果。官方说明的部位额度为头饰 1、武器与盾牌合计 2、铠甲 1、披肩 1、鞋类 1、饰品 2，且受总上限约束。实际接受与否由服务器决定。 |
| 协议兼容字段 | 保留 `activate`、`enable` 及对应请求构造、回包处理。官方模板里残留的效果按钮区域由 CSS 隐藏；组件只绑定并发送充能、加入、移除三个写操作。没有对玩家开放的手动激活、逐页激活、多卡组存储或一键切换。 |

依据为[官方卡片组件](https://github.com/parkerjj/LROBrowser/blob/8e667880943a80a1cbf550407944e4ca270d56da/modules/UI/Components/CardConnection/CardConnection2.js)、[界面模板](https://github.com/parkerjj/LROBrowser/blob/8e667880943a80a1cbf550407944e4ca270d56da/modules/text_UI/Components/CardConnection/CardConnection2.html.js)、[样式](https://github.com/parkerjj/LROBrowser/blob/8e667880943a80a1cbf550407944e4ca270d56da/modules/text_UI/Components/CardConnection/CardConnection2.css.js)和[包结构](https://github.com/parkerjj/LROBrowser/blob/8e667880943a80a1cbf550407944e4ca270d56da/modules/Network/PacketStructure.js)。本版引用 `DB/Card_Connection_db2`，归档内可找到的 `Card_Connection_db.js` 是不同模块，原始 bundle 也只引用 `db2`。据此核实 UI 和协议语义，实服全量目录的分类、页序和槽位映射需要另行验证。

| 界面或行为 | 结论 | 拟调整 |
| --- | --- | --- |
| 七分类、全部／已充能／可充能、按名称或 ID 搜索、卡图和右键说明 | 官方功能。计数、分页、空列表提示是客户端增强。当前「可充能」另核对背包物品类型和正数量，并支持刷新当前视图。 | 保留。类别全览可以分页，界面统一使用浏览页码。搜索、分类和卡组共享动作与状态判断。 |
| 充能、加入、移除 | 三项都走真实协议。当前全屏层没有显示官方充能确认框，点击直接发包。分类和搜索的未持有卡也能出现充能按钮。 | 恢复面板内的「消耗 1 张」确认。无库存时显示「背包没有此卡」，单次确认只发一次。加入／移除直达当前卡组，保留各自的确认结果。 |
| 「我的卡组」、八槽位、已充能待加入汇总 | 八槽属于官方卡组。跨分类汇总是客户端优化。当前横栏选中的本地草稿接管了左侧 `n/8`、槽位与加入目标。 | 「我的卡组」和 `n/8` 始终展示服务器确认的组。汇总只显示当前可加入的已充能卡，已经在组里的卡显示「已加入卡组」。 |
| 四格搭配、保存、双击改名、切换、快捷键、结果提示 | 可实现的客户端增强。保存是按服务器、账号、角色隔离的本地 Preferences。切换逐张先移除差异，再加入差异，并核对最终组。快捷键当前要求保存且曾确认的搭配。 | 明确使用「卡组方案」「保存当前卡组」「切换到此方案」「重命名」「当前方案」。保留快捷键和已有保存数据。空位表示「未保存」，点击它没有清空卡组的副作用。已明确保存的空方案若保留，可在切换会清空当前卡组时明确提示。 |
| 「激活」「先激活卡册」「未激活」「卡册生效」「已激活（服务器）」「已启用（服务器）」 | 客户端混用了预设选择、卡组归属和兼容字段。现在的「激活」实际会切换卡组，且能把未保存的空预设当作空目标，逐张移除当前卡。 | 去掉激活和启用状态。仅用「已充能」「已加入卡组」「未保存」「当前方案」描述可确认的状态。取消编辑现用卡组对预设的依赖。 |
| 「本页效果」「8 张全部充能自动激活」与「同类装备仅 1 张生效」 | 逐页凑齐获得效果缺乏这版官方入口与行为依据。侧栏那句把「与装备上相同的卡片只生效一份」误写成按装备类别只生效一张。 | 删除逐页效果提示。按官方原意简述重复卡效果及部位、总量限制，服务器拒绝时显示已知原因。 |
| LRO 助手「卡册一键切换」 | 可选的第二入口，自己保存最多 20 套，另一套预检和写入编排。底层又调用卡片组件 `sendAction`，可能被原有的「先激活」门槛拒绝。 | 两个入口和快捷键共用一个卡组切换执行器，兼容助手旧存档和内置四格，继续按已有身份隔离。四格 UI 不截断助手存量。 |

## 新卡故障定位

1. **背包持有、典藏充能、写入是否等待是三个独立状态。** 官方「可充能」渲染时调用背包 `getItemById`。本地有 `setItems/addItem/removeItem/updateItem/onRemove` 刷新钩子，范围是打开的「可充能」视图。当前普通拾取调用 `InventoryController.getUI().addItem(pkt)`，离线覆盖这条背包变化路径。截图已显示克瑞米卡片 `4040` 属于「可充能」，卡面「未充能」符合尚未消耗的状态。
2. **已复现持续等待如何拦住新卡。** 本地将充能、加入、移除和方案切换共用同一等待状态。没有匹配回复的请求在 5 秒后进入 `unresolved`，下一张卡即使已显示可充能，点击也直接返回 `false`，底栏显示「正在等待服务器确认，请稍候」。离线模拟旧卡无回复、随后点 `4040`，发送次数保持 1；更换连接并应用完整卡册列表后重试，发送次数增至 2。截图和复现一致，但还无法确定该用户是正在正常等待、已超时，还是触发了其他入口。
3. **需要定位玩家当时的第一处分歧。** 目前确认筛选逻辑和请求拦截链。实服需要按顺序对齐物品入包、点击是否发包、回包是否解码并匹配 `tab/level/cardid/state`、背包是否扣卡和完整列表是否通过目录校验。目录页数不一致会使 `fullSnapshot` 拒绝整份列表；这是需检查的独立分支。客户端目前只匹配一种加入卡组的文本拒绝，充能拒绝是否有专用回包或消息需要现场证据。

## 实施顺序与验收

### P0 · 拆开背包刷新与写入等待

- [ ] 在现有 `vendor/v2/Online.js` 物品流与 `scripts/lastro-card-state.mjs` 核对入包记录。对问题来源按「新堆叠／已有堆叠」记录简短的开发诊断，只记录物品 ID、数量、入口与时间顺序。覆盖拾取、邮件领奖、购买或 NPC 发放等实际获得方式以及卡片消耗，复用原生背包事件和当前刷新逻辑。新入包卡在打开的「可充能」即时出现，分类/搜索重新计算动作可用性，页面滚动位置不跳。
- [ ] 在 `scripts/lastro-card-deck.mjs` 区分待回复、明确拒绝、超时待核实以及卡册尚未同步。复现并确认当前发送返回值与回包匹配路径。先保留同一卡请求的关联保护，再解除无关卡长期受旧请求阻塞；不同卡能否继续走独立充能要用实测回复形态验证。对结果不明的原请求保留对应的限制，迟到回包或完整快照到达后校正。充能可能已经消耗卡片，超时禁止自动重发。加入与充能共用回包类型，需按操作、会话、坐标和服务器权威状态关联。
- [ ] 在 `vendor/v2/lastro-card-collection-ui.mjs` 使用面板内确认和明确结果文案。实际发包后才显示「正在充能」，回包成功后列表从「可充能」迁移到「已充能」，扣库存和状态回包先后次序均正常。明显失败显示已知原因，超时显示结果待确认。

### P1 · 恢复官方卡组语义和文案

- [ ] 在 `vendor/v2/lastro-card-collection-ui.mjs`、`scripts/lastro-card-state.mjs`、`scripts/lastro-card-deck-ui.mjs` 收敛分类、搜索和卡组动作。根据背包数量与典藏状态判定是否可充能，卡组八槽与加入状态取服务器确认内容。去掉激活、启用及逐页效果的玩家文案，协议兼容字段继续解析。用「第几页」做目录定位时，按页面实际导航展示，避免把底层 `level` 当作用户需要理解的效果等级。
- [ ] 在 `scripts/lastro-card-deck.mjs` 允许直接加入和移除当前卡组，删除先选或应用本地预设才能编辑、才能保存的限制。验证新角色、已有卡组且没有本地方案、已有方案却选择了其他方案、有同 ID 不同目录坐标和部位拒绝的情况。

### P2 · 保留一键切换并统一执行

- [ ] 在 `scripts/lastro-card-deck.mjs` 与 `scripts/lastro-card-deck-hotkeys.mjs` 用同一个入口切换已保存的方案。逐张提交前预检目标的充能状态、可靠坐标、角色与连接；仅发送所需增删。相同方案发零个包。部分失败立即停止，显示当前实际卡组与失败原因。已有预设、名称、快捷键继续可读，旧的 `verifiedCards` 仅作为已有确认记录使用，界面不要求玩家执行所谓「激活」。
- [ ] 让 `src/assistant/lro-assistant-standard.mjs` 与 `src/assistant/lro-assistant-features.mjs` 复用同一个执行器和确认状态，移除重复的轮询执行以及遇到同 ID 直接取首项的逻辑。助手已保存方案继续能读取和切换，保留现有存储隔离和名称。两个入口并发发起的切换同样由同一个执行器排队或拒绝。

### 验证范围

- [ ] 用 `test/lastro-card-state.test.ts`、`test/lastro-card-deck.test.ts`、`test/lastro-card-deck-hotkeys.test.ts`、`test/lastro-card-collection.test.ts`、`test/lastro-network-compatibility.test.ts` 覆盖原生拾取、消费与回包顺序、ACK 迟到、没有 ACK、缺少或异常全量快照、换图及换角色。验收一次 `4040` 原故障流程，以及未持有、已有重复堆叠、容量满、部位拒绝、切换中断、空方案和旧方案。
- [ ] 相关 Vendor UI、数据测试和助手测试通过后，运行 `pnpm lint`、`pnpm typecheck`、`pnpm test`、对应目标本地构建及 `pnpm audit:iwa`。在受影响的服和连接模式上确认不小退即可充能。覆盖 App 服官方中转与直连、二转和三转传统模式；用实测目录验证 `tab/level`。沿用现有模块，避免新增构建脚本或引入运行时网络依赖。

调查时以本地代码和离线回包进行验证。卡片典藏相关 Vitest 250 项、网络兼容 Vitest 55 项、Vendor 卡片测试 21 项、助手测试 45 项均通过。实服故障触发条件与当前 `db2` 全量目录待验证。
